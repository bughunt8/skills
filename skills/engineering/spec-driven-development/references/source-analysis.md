## Advantages, tensions, adopted and rejected choices

| Concern | Tension | Decision |
| --- | --- | --- |
| Constitution-first versus immediate PRODUCT/TECH | Different entry artifacts need not create competing authorities. [Jay upstream](https://github.com/jaydoubleu/agentskills/tree/main/.claude/skills/spec-driven-development) [Lloyd article](https://www.linkedin.com/pulse/three-skills-you-need-spec-driven-development-zach-lloyd-bdhvc) | Review global principles/mission first, then split what/how. INDEX can point to PRODUCT and TECH issue files. |
| Addy's broad spec content versus behavior-only EARS | Commands, tree, style, and stack are useful but are implementation details. [Addy SDD](https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md) | Retain every concern in TECH_STACK, CONSTITUTION, or DESIGN rather than polluting SPECIFICATION. |
| Phased approval versus convenient continuous automation | A saved spec is not consent to plan or implement. [Addy SDD](https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md) | Explicit later-turn spec approval, separate design/task approvals, immutable hash-bound final authorization, and default stop after one atomic task. Scoped unattended continuation requires explicit human policy and cannot waive safety/drift gates. |
| Multi-feature hierarchy versus single-capability overhead | Global hierarchy is wasteful for a small feature but avoids monoliths when capabilities can ship separately. [Jay upstream](https://github.com/jaydoubleu/agentskills/tree/main/.claude/skills/spec-driven-development) [Addy SDD](https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md) | Flat all-nine default; four shared globals plus feature folders for multi-capability requests. Human approves stable module IDs, DAG, and provider-owned boundaries before feature specification. |
| External spec formats versus machine structural checks | Format reuse does not mean arbitrary prose can be parsed reliably. [Addy SDD](https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md) | INDEX maps exact H1/H2 bodies. Document incompatible format limits; allow an explicitly reviewed thin projection without pretending to understand every external format. |
| Invariants and actual red versus generated stubs | Test intent, a NotImplemented exception, and a genuine behavior assertion failure are different evidence. [Jay upstream](https://github.com/jaydoubleu/agentskills/tree/main/.claude/skills/spec-driven-development) [Lloyd article](https://www.linkedin.com/pulse/three-skills-you-need-spec-driven-development-zach-lloyd-bdhvc) | Distinct positive/violation tests per invariant; actual red, green, refactor logs; integration/contract checks where applicable. Reject claiming generated stubs prove real red or semantics. |
| Simplicity versus arbitrary structural limits | Jay's simplicity discipline is useful, but a fixed module-count limit can conceal necessary boundaries. [Jay upstream](https://github.com/jaydoubleu/agentskills/tree/main/.claude/skills/spec-driven-development) | Justify complexity, dependencies, and abstractions in DESIGN. Do not enforce an arbitrary maximum of three modules; choose independently testable boundaries through human review. |
| Prototype feedback versus production implementation | Lloyd's workflow can use product feedback and prototyping before final technical decisions. [Lloyd article](https://www.linkedin.com/pulse/three-skills-you-need-spec-driven-development-zach-lloyd-bdhvc) | Optional exploratory prototype work needs explicit approval, isolated scope, and non-shipping status. It never substitutes for approved behavior/design/tasks or authorizes production code. |
| UI screenshots versus tested user interaction | Static intent cannot show keyboard or actual runtime behavior. [Lloyd article](https://www.linkedin.com/pulse/three-skills-you-need-spec-driven-development-zach-lloyd-bdhvc) | Keep mocks/screenshots in DESIGN and require actual browser/keyboard evidence for UI execution. No UI or UI telemetry obligations when explicitly N/A. |
| Independent tasks versus prerequisites | Independent work is compatible with explicit dependency order. [Addy SDD](https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md) | Check task DAG, verified prerequisite evidence, and owned paths. Reject a blanket rule that all tasks have no dependencies. One-task default limits agent execution, not design parallelism. |
| Living specs versus rewriting them to excuse code | Specs may evolve only through deliberate reviewed decisions. [Addy SDD](https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md) [Lloyd article](https://www.linkedin.com/pulse/three-skills-you-need-spec-driven-development-zach-lloyd-bdhvc) | Append contradiction evidence to CROSS_ANALYSIS, offer human choice, refresh reviews and approvals after intentional amendments, and reference affected IDs in PRs. Reject silent reconciliation. |
| Source rhetorical certainty versus actual engineering evidence | Natural language guides work; it does not guarantee identical code or formally safe execution. [Jay upstream](https://github.com/jaydoubleu/agentskills/tree/main/.claude/skills/spec-driven-development) | No deterministic-generation, automatic-correctness, security-proof, or formal-safety claim. Structural lint is explicitly distinct from manual semantic/code/test review. |

## Changes to the user's draft

| Draft concern | Preserved or amended | Reason |
| --- | --- | --- |
| CONSTITUTION, MISSION, TECH_STACK, ROADMAP, SPECIFICATION, DESIGN, INVARIANTS, OBSERVABILITY, TASKS | All nine named files and templates preserved | Retains the requested mental model and command targets; mappings avoid duplicate authority. |
| `/constitution /spec /plan /tasks /analyze /build` | Preserved with strict write boundaries | A phase cannot silently begin implementation or authorize an unrelated phase. |
| EARS behavior | Per-row declared pattern and syntax, plus AC traceability | Correct keyword order and nonempty system/response matter more than allowed totals. Grammar is not semantic adequacy. [Official EARS](https://alistairmavin.com/ears/) |
| No code/database details in behavior spec | Best-effort blocker, manual review still mandatory | Implementation belongs in design; a short lexical check cannot detect every indirect prescription. |
| Invariants and TDD | Positive and attempted-violation tests; actual red evidence | Prevents treating "tests exist" or an import failure as proof of behavior coverage. |
| Structured telemetry | Runtime app events with privacy policy/tests; CLI output allowed | Prevents an impractical stdout ban and unnecessary UI analytics. Explicit opt-outs are supported. |
| Dependency rules | Acyclic explicit task/module DAG; independent tasks allowed | Avoids a false "no dependencies" rule while preserving prerequisite verification. |
| One task then stop | Default one atomic task, update execution log, human verification | Bounded review makes task results and failures visible. No automatic commits/posts/deploys. |
| Cross-analysis and approval | Append-only review history, hash freshness, human authorizer | Prevents erased contradictions and stale authorization. Local files still do not authenticate a human. |
| Spec readiness versus code review | Pre-build structural tasks stage and post-build ready stage | Planned files can be absent before TDD; actual code/tests and evidence are separately inspected after build. |

## Existing-script reuse

The existing spec_generator makes one combined RFC2119 document, and spec_validator scores that combined format. They stay unchanged and are optional for projects deliberately retaining that older contract. They are not EARS split-artifact checkers; translating their score into approval would be misleading.

The new [bounded adapter](../scripts/sdd.py) uses the existing `test_extractor.SpecParser` when installed next to the canonical `engineering/skills/spec-driven-workflow/scripts/test_extractor.py`. It normalizes only the AC-N/GWT section wrapper, retains REQ references, independently checks complete GWT and requirement coverage, and labels extraction mode. Standalone installation uses the bounded GWT fallback, without an absolute repository path or bundled upstream source. The existing generators are not automatically called, and extraction intent is not a test run. [Adapter implementation](../scripts/sdd.py)

The new checker covers gaps in that older behavior: nine-artifact structural lint, EARS types, invariant/observation ID matching, DAGs, symlink-safe no-clobber scaffold, content-freshness checks, and local approval gates. Semantic and implementation review remain manual. [Checker and executable tests](../tests/test_sdd.py)
