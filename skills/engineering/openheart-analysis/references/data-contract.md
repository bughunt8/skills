# Normalized data contract

`schemas/analysis.schema.json` is generated by `scripts/contract.py`. It is a
JSON Schema 2020-12 document. The Python tooling implements the subset used by
this schema and then checks cross-record and source invariants. It has no
runtime dependency outside the Python standard library.

## Root and evidence

| Field | Meaning |
| --- | --- |
| schema_version | Exactly `1.0` |
| source | Target repository label, revision, scope, languages and exclusions |
| files | Included relative paths, lowercase SHA-256, nonnegative line counts, `encoding: utf-8` and `role` |
| stages | All ten named stage objects |
| diagrams | All 20 catalogue graph slots, including the additional AST view |
| limitations | Explicit analysis, coverage and interpretation gaps |

An evidence entry has `file`, `line_start`, `line_end` and `excerpt`. The validator
checks that the excerpt occurs inside the inclusive source range and that the
whole file matches its declared hash and line count. This is source consistency,
not independent proof that a relationship follows from that excerpt.

Only UTF-8 text files are supported. Normalize CRLF and lone CR to LF for line
numbering; split only on LF, not form feeds or Unicode separators. A final LF
does not add a phantom line. Empty files have zero lines and no evidence spans.
`role` is `source`, `trace`, `snapshot` or `specification`. Observed records need
trace/snapshot evidence; role assignment itself still requires semantic review.
Source scope/exclusions use exact paths, directory prefixes or shell-style
globs, with `.` meaning the whole root. Included files must be in scope and not
excluded. Revision text is declared by the agent, not verified against Git by
the Python helper.

All stage and diagram graphs have `status`, `reason`, `method`, `nodes` and
`edges`. Status is one of `complete`, `partial`, `insufficient_evidence`,
`not_computed`, `not_requested`. `method` records parser/solver/manual
reconstruction and relevant versions. For incomplete statuses, explain the gap
in `reason`. In an empty graph `complete` is forbidden.

## Nodes and edges

Each node has `id`, `label`, `kind`, `basis`, `parent`, `evidence`, `fields`,
`methods` and `attributes`. `basis` is `source`, `derived`, `inferred` or
`observed`. `parent` is a node ID within the same graph or null. A member has
`visibility`, `name`, `type_name`, `signature`, `is_static`, `is_final`.

Each edge has `id`, `source`, `target`, `kind`, `label`, `basis`, `evidence` and
`attributes`. Endpoints must exist within that graph. Both nodes and edges need
at least one evidence object. Derived records explain their calculation in
`attributes`; inferred records remain partial. Observed runtime facts require
provided trace/snapshot files in the input inventory.

Stage IDs are globally unique across stages. Diagram records reuse stage IDs
only for identical complete records, including basis, parent, attributes,
members and evidence; different views may select different subsets.
The validator rejects certainty, resolution or attribute changes under a
reused ID. A diagram node
may also introduce a supported UML abstraction with a new ID and its own
evidence. Do not claim such a node is a compiler-produced entity.
The validator cannot detect a contradictory claim deliberately introduced under
a new ID. Nonblank excerpts, derivations, methods and file roles are structural
requirements, not machine-established semantic truth. Independent review must
check whether they actually justify each relationship.

## Stage record dictionary

These attributes retain upstream concepts in text form. Use only fields known
for a record and explain unavailable fields in the stage reason/limitations.
The flexible `attributes` object deliberately does not imply binary layout
compatibility. Its semantic contents require review beyond schema validation.
Global kind enums are machine-enforced, as are per-stage kind restrictions,
AST `node_type`, callsite `resolution`, BDD child references, Boolean terminals,
derived-record `derivation` and positive message ordinals. Remaining attributes
are a flexible typed envelope, not complete compiler record schemas.
The JSON Schema alone cannot enforce references, source consistency or
uncertainty propagation. Run the bundled validator for those additional checks.
It requires native JSON integer spellings for line/ordinal values, not `1.0`.

| Stage | Node kinds and expected attributes | Edge kinds |
| --- | --- | --- |
| ingestion | `token`: token_id, text, token_type, line, column, length, tokenizer | `next_token` |
| syntax | `ast`: node_type, preorder, first_token, last_token, operator, parser | `contains` |
| symbols | `symbol`, `scope`, or explicit `class`/`interface` declaration aliases: qualified_name, symbol_kind, visibility, modifiers, type_ref, scope_id, owner, parameters, imports | `declares`, `extends`, `implements`, `type_use`, `contains` |
| control_flow | `block`: function_id, statements, first_token, last_token, entry, exit, idom, dominance_frontier | `control_flow`, `true`, `false`, `loop_back`, `exception` |
| data_flow | `ssa`, `phi`: original_symbol, version, definition, block_id, phi_args, flags | `data_flow`, `def_use`, `control_dependence` |
| calls | `callsite`, `symbol`: caller, callee_candidates, dispatch, resolution, arg_count, call_node, receiver_ssa, scc, points_to | `calls`, `candidate_call`, `recursion` |
| traceability | `trace`: layer, entity_id, source_range, token_range, supported_ids | `source_of`, `projects_to` |
| paths | `bdd`, `terminal`: function_id, formula, variable_order, variable, root, terminal, low, high, sat_count, bound, assumptions | `low`, `high` |
| uml | `class`, `interface`, `package`, `component`, `object`, `action`, `state`, `actor`, `port`, `usecase`, `pattern`: classifier/role/scenario attributes | UML relationships and scenario messages |
| unified | Any supported node kind, with originating stage and IDs | Consolidated relationships |

Source files and phase status are mandatory even when stage records are empty.
The exporter emits every requested diagram's JSON plus a labelled status-only
Mermaid/PlantUML artifact when evidence is insufficient. The status label is
reporting metadata, not an invented code entity.

## Output files

`init` emits `analysis.json`, `REPORT.md` and `VALIDATION.md`. `export` emits
`analysis.json`, `diagrams/<id>.json/.mmd/.puml`, provisional `diagrams/ACT.*`
activity aliases, `traceability.json`, `report.json`, `REPORT.md`,
`VALIDATION.md`, and optionally the limited class XMI.

`traceability.json` has `by_entity` and `by_file`. `report.json` records source,
stage/diagram status, coverage, counts, limitations and format losses. The
exporter never sets a blanket `verified: true` or claims semantic accuracy.
